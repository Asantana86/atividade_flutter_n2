1. O que é este aplicativo?

O ServiceFlow é um app mobile (Flutter) para técnicos e gestores registrarem e acompanharem ordens de serviço (O.S.). Ele permite:

  • Fazer login com conta segura (Supabase)
  • Cadastrar clientes, técnicos, serviços e usuários
  • Abrir, iniciar e finalizar ordens de serviço
  • Tirar fotos e coletar assinatura digital como evidência
  • Trabalhar sem internet: os dados ficam no celular e sincronizam quando a rede voltar

O foco da arquitetura é reaproveitar código: regras comuns ficam em classes base no núcleo (core), e cada funcionalidade (módulo) só implementa o que é específico.

2. Visão geral da arquitetura

O projeto segue uma arquitetura em camadas, organizada por pastas:

CamadaPastaO que faz (em linguagem simples)
Entrada do applib/main.dartLiga o Supabase, o banco local e a sincronização antes de abrir a tela
Interface globallib/app/shared/Rotas, tema e widgets reutilizáveis
Regras e dadoslib/app/core/Modelos, validações, serviços, repositórios, HTTP, sync
Telas por funçãolib/app/modules/Login, dashboard, clientes, O.S., etc.

Fluxo de uma operação típica (ex.: salvar um cliente)

  1. Page (tela) — o usuário preenche o formulário e toca em Salvar.
  2. Controller — recebe a ação, mostra loading e trata erros.
  3. Service — aplica validações de negócio e chama o repositório.
  4. Validation — confere campos obrigatórios e regras.
  5. Repository — grava ou lê no SQLite (banco no aparelho).
  6. Schedule + Provider — em segundo plano, envia para o Supabase na nuvem.
Page/UI → Controller → Service → Repository (SQLite)
                ↓                              ↓
         Loading/erros                   is_sync = 0
                ↑                              ↓
         Feedback (SnackBar)          BaseSchedule → BaseProvider (nuvem)

4. Inicialização do aplicativo (main.dart)

  1. WidgetsFlutterBinding — prepara o motor do Flutter.
  2. Supabase.initialize — conecta autenticação e API na nuvem.
  3. Somente em mobile (não na web): DatabaseHelper, LogService, SyncSystemInitializer.
  4. runApp(AppWidget) — exibe o app com rotas e tema.

A tela inicial é a Splash, que redireciona para login ou dashboard.

5. Classes base (o esqueleto do projeto)

5.1 BaseModel

Toda entidade de negócio herda dela.

CampoSignificado
idIdentificador do registro
createdAtData de criação
isSync0 = não sincronizado; 1 = sincronizado com a nuvem
ativotrue = ativo; false = desativado (exclusão lógica)

5.2 BaseRepository

Centraliza operações no SQLite: insert, update, delete, findAll, findById, softDelete, findAllPendingSync.

5.3 BaseValidation

Valida campos e regras antes de criar ou atualizar.

5.4 BaseService

Orquestra o CRUD: validação → hooks before/after → repositório.

5.5 BaseController

Liga a tela ao serviço; gerencia isLoading e tratamento de erros.

5.6 BaseProvider

Comunicação com Supabase: syncToCloud, fetchFromCloud, deleteFromCloud.

5.7 BaseSchedule

Motor offline-first: timer (5 min), detecta internet, envia pendentes e baixa atualizações.

8. Sincronização offline-first

  1. Salvar sempre no SQLite com is_sync = 0.
  2. ScheduleManager registra um schedule por entidade.
  3. Com rede: upload de pendentes e download de novidades; marca is_sync = 1.
  4. Dashboard pode forçar sync com SyncSystemInitializer.forceSyncAll().

9. Rede e segurança

  • Supabase — autenticação e API REST
  • Dio (AppClient) — HTTP com interceptors de auth e erro
  • Token — armazenado com flutter_secure_storage

12. Resumo

  • App modular: cada pasta em modules/ é uma funcionalidade.
  • Core concentra classes base, sync e HTTP.
  • Padrão Page → Controller → Service → Validation → Repository.
  • Nuvem via Provider + Schedule, sem a tela lidar com rede.
  • Offline-first para trabalho em campo.
